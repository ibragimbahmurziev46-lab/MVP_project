Время и дедлайн
Общий объём темы: 6 академических часов.
В это время входит теория, разбор примеров, выполнение контрольной точки и защита.
Распределение времени:
теория и разбор Git workflow - 2 академических часа;
выполнение контрольной точки и защита - 4 академических часа.
Крайний срок сдачи: до выдачи следующей контрольной точки.
Дата отдельно не указывается. После выдачи следующей контрольной точки работа считается сданной после дедлайна.
Инструментальные средства
Для выполнения работы использовать:
Git;
GitHub;
терминал, Git Bash или встроенный терминал IDE;
GitHub Network для просмотра графа веток;
Markdown-файл README.md для краткого описания результата.
Проектная тема
Перед началом работы фиксируется индивидуальная проектная тема. Одинаковые темы в группе не допускаются.
Зафиксированная тема используется дальше во всех проектных практиках:
Git -> Linux -> Docker -> Docker Compose -> Архитектура -> Финальный проект1text
Варианты проектных тем:
сервис задач;
библиотека книг;
учёт расходов;
трекер привычек;
мини-магазин;
сервис бронирования;
система заявок в поддержку;
сервис заметок;
учёт складских товаров;
трекер учебных курсов.
Можно предложить собственную тему, если она не повторяет тему другой работы.
Минимальный результат
В конце работы должен быть один GitHub-репозиторий под выбранную тему.
Пример для темы сервис задач:
task-service/ README.md project-notes.md api-plan.md1234text
Файлы могут быть простыми. Главная задача данной контрольной точки - показать работу с Git: коммиты, ветки, merge, конфликт и граф веток.
Как показать результат и что сдать
Показать результат нужно через GitHub-репозиторий.
На проверке должны быть видны:
публичная ссылка на репозиторий;
история коммитов;
минимум 3 ветки;
merge между ветками;
конфликт и коммит, где он был исправлен;
граф веток в GitHub Network.
Сдать нужно ссылку на GitHub-репозиторий.
В репозитории должны быть:
README.md с названием проектной темы и кратким описанием;
рабочие файлы проекта по выбранной теме;
git-conflict.md или отдельный раздел в README.md с описанием конфликта;
скриншот графа веток git-network.png или ссылка на GitHub Network.
Этапы
Зафиксировать индивидуальную проектную тему.
Создать публичный репозиторий на GitHub с понятным названием проекта.
Добавить стартовые файлы: README.md, project-notes.md, api-plan.md.
Делать изменения маленькими шагами и собрать минимум 6 осмысленных коммитов.
Создать минимум 3 ветки для разных изменений.
Выполнить минимум 1 merge в main.
Специально изменить одну и ту же строку в двух ветках, чтобы получить конфликт.
Исправить конфликт вручную и сделать отдельный commit с исправлением.
Открыть GitHub Network и проверить, что граф веток виден.
В README.md или git-conflict.md кратко описать, где был конфликт и как он исправлен.

Защита
На защите рассказать про свой репозиторий:
какая проектная тема была зафиксирована;
почему выбрана тема;
какая начальная структура проекта добавлена в репозиторий;
зачем были созданы ветки и чем они отличаются;
какие изменения фиксировались в коммитах;
где возник конфликт и как он был решён;
как по графу веток понять выполненный workflow.
Оценка
5 баллов - работа сдана до дедлайна и все критерии выполнены.
До 5 баллов - работа выполнена, но сдана после дедлайна, либо выполнена только часть ключевых требований.
0 баллов - нет рабочего репозитория или история Git не подтверждает выполнение задания.
